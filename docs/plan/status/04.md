## Decisions

1. **Metadata per class, made on first use.** `Schema()` returns a base class that holds
   `[META]` as an own data property (the contract), but the class the developer writes
   extends that base and the base cannot know it. The first `meta(User)` gives `User`
   metadata of its own: the same field tables, the name `"User"`, its own associations
   (scanned from `User` and its ancestors), and a factory that makes instances of `User`.
   It is stored as an own non-writable property `User[META]`. A class that extends `User`
   gets its own the same way, inheriting the associations. **Other steps must get
   metadata with `meta(S)`, not `S[META]`**, until a first `meta(S)` has run (see
   Requests).
2. **The row factory is a constructor whose `prototype` is the class's.** Rows are
   `instanceof User` and getters work, and no user constructor runs. Field names enter the
   generated function as string literals (`JSON.stringify`), so no schema can inject code;
   a test proves it.
3. **The constructor throws `SchemaDefinitionError`** pointing at `cast` and `change`,
   for the base and for any subclass (a subclass constructor must call `super`).
4. **A nullable field has `default: undefined` in its metadata**, not `{ value: null }`.
   The spec's table says "default becomes null"; that is what a new record's value is
   (step 05's `getField`), but writing an explicit `null` on insert would override a
   database default (`posts.published DEFAULT false`). `.nullable().default(null)` is
   available when the explicit null is wanted.
5. **`.primaryKey()` implies `dbGenerated` for a column of kind `integer` or `bigint`**
   (custom types included), when it is the only key field. Combined with `.autogenerate()`
   it is refused, with the fix (`{ dbGenerated: false }`). In a composite key an integer
   part must say which it is (`{ dbGenerated: false }` or `.dbGenerated()`), because the
   implied rule would make every part optional and the insert would fail far from the
   cause. A float key must pass `{ dbGenerated: false }`: the types call it generated, the
   database never generates one.
6. **`.autogenerate()` without a function**: UUID v7 for `t.uuid()`, the current time
   (cast through the type, so `precision: "s"` drops milliseconds) for a timestamp type,
   `SchemaDefinitionError` otherwise. The spec's "option for v4" is
   `.autogenerate(() => crypto.randomUUID())`, documented in the guide; I added no option.
   UUID v7 is ordered to the millisecond, not within one.
7. **`timestamps()`**: `createdAt` has `autogenerate.on = "insert"`, `updatedAt`
   `"insertAndUpdate"`. `type` must be an unmodified type whose cast takes a `Date`.
8. **`t.embedMany` defaults to a fresh `[]`** (so it is optional in `InsertShape`);
   `t.embedOne` has no default. The field type of an embed is `json` (jsonb) for now;
   step 15 owns how embeds are cast and stored. Embed `onReplace` is `"error"`,
   `"invalid"`, `"update"` (one only), `"delete"`, as the embeds guide says.
9. **Embedded schemas name their JSON keys like columns**: snake_case by default, with
   `naming` and `.column()`. This follows D4; the owner may prefer field names as keys.
   Step 15 reads `FieldMeta.column`. An embedded schema has no primary key requirement,
   and declaring an association on one is a `SchemaDefinitionError`.
10. **`naming`** is `"snake_case"` (default), `"camelCase"` (field names as they are) or a
    function. The guide listed only `"snake_case"`.
11. **Association option types check field names.** `foreignKey` of `hasOne`/`hasMany`,
    `references` of `belongsTo`, `where` and `orderBy` keys, and a join schema's
    `joinKeys` and `joinWhere` must be fields of the right schema, at compile time.
    This works through circular schemas (the blog compiles). `belongsTo`'s `foreignKey`
    is on the owner, which the types cannot see from a static initialiser, so it is
    checked only at resolution.
12. **`orderBy`** takes field names and `{ field: "asc" | "desc" }` objects:
    `["title", { createdAt: "desc" }]`.
13. **Resolution** (first `assocs()` call) checks: the target thunk (a class given
    instead of a thunk, a thunk that throws, one that returns no schema, an embedded
    target), unknown option names (so `onDelete`, `optional` and `preloadOrder` are
    reported), foreign and referenced fields exist and are stored, key counts, key types
    (`integer` and `bigint({ mode: "number" })` match, both being JS numbers; `bigint`
    does not match either), `onReplace` per kind (`update` only to-one; `manyToMany` only
    `error`, `invalid`, `delete`), `where`/`orderBy` fields, the `manyToMany` rules (a
    single-field key on both sides, `joinKeys` with a table, inference from the join
    schema's `belongsTo`, refused when ambiguous or self-referential), `through` paths
    (at least two steps, nothing else beside them, every step exists, the path ends at
    the declared target), and names (not a field, not reserved, not `fields`). A failure
    is not cached, so the next call reports it again.
14. **Resolution is re-entrant and does not depend on order.** It runs in rounds (plain
    keys, then join tables, then `through` chains, then the chains' checks). A schema that
    asks for this schema's associations while they are being resolved gets the map built
    so far (a join schema reads the owner's `belongsTo`). A `through` path is followed
    through the *declarations* of the schemas on it, never their resolved associations,
    so the result is the same whichever schema is asked first, and a mistake elsewhere on
    the path is reported by that schema's own resolution. Tested in both orders.
21. **A class member may not share a name with a field or an association.** A getter or
    method of that name on the class's prototype chain would hide the row's own property
    or make it impossible to set (a generated factory would lose the value silently). It
    is refused with `SchemaDefinitionError` when the class is first used (`meta(S)`) or
    its associations are resolved. TypeScript already rejects such a member in a class
    body; this covers plain JavaScript and members added to the prototype. The generated
    factory is also strict code now, as the loop is.
15. **`unique`** of `manyToMany` is kept as an extra member of the resolved association
    (`ResolvedAssoc`), because the frozen `AssocMeta` contract has no member for it.
    `AssocMeta.defaults` is always `undefined`: no step file gives an option for it.
16. **`toJSON` copies all the way down**: nested rows become plain objects through their
    own `toJSON` (so a class may override it), arrays are copied, other values are kept as
    they are. A redacted field is left out at every level.
17. **Inspect** uses `Symbol.for("nodejs.util.inspect.custom")` (no import of
    `node:util`), shows `ClassName { … }` with `**redacted**` unquoted, honours `depth`,
    and falls back to `formatStruct` where no inspect function is passed.
18. **`primaryKeyOf(row)` returns `unknown`; `primaryKeyOf(row, User)` is typed**
    `PrimaryKeyOf<typeof User>`. A row's type does not lead back to its class, so the
    one-argument form cannot be typed without changing the contract.
19. **`rowMeta` keeps at most 4,096 database schemas per table**, then starts again, so
    a tenant per database schema cannot grow it without bound. Past that limit the same
    arguments may return an equal object that is not the same object.
20. **Blog schemas follow `blog.sql`**: keys and foreign keys are
    `t.bigint({ mode: "number" })` (the tables use `bigserial`); `posts.tags` is the field
    `tagList` with `.column("tags")`, because `tags` is the many-to-many association;
    `posts.published` and `posts.views` are nullable with defaults, as in the DDL;
    `users.settings` is an embed (`UserSettings`), which gives the blog its embed;
    `Org.id` is a client-generated UUID v7.

## Review, round 1

The reviewer requested changes on PR #11 at `2168977`: three blocking findings and three
suggestions. All were taken.

1. A getter named like a field made the generated factory drop the value silently (and
   the loop throw). Refused now (decision 21); the generated function is strict.
2. Association resolution depended on which schema was asked first: a join schema's
   `through` that went back through the owner saw the owner's half-built map. Paths are
   now followed through declarations (decision 14); a test runs both orders.
3. A composite key of integer fields made every part database-generated. Refused now,
   with the fix (decision 5).
4. The rule that `integer` and `bigint({ mode: "number" })` keys match had no test that
   failed without it. Added, with the refusal of `integer` against a plain `bigint`.
5. A float key is refused without `{ dbGenerated: false }` (was a known gap).
6. The UUID generator stored for `.autogenerate()` took an argument as the time. It is
   wrapped now.

## Known gaps

- **That `ROW` is the last own property is not tested.** Moving it first in the generated
  function passed every test: `Reflect.ownKeys` always lists symbols after strings, and
  V8 cannot compare hidden classes of rows from two different factories. Both factories
  assign it last, by reading.
- In a composite key, `.primaryKey().dbGenerated()` on an integer part is typed as
  optional on insert while `.primaryKey()` alone is refused; the types cannot see the
  other key fields, so `t.integer().primaryKey()` in a composite key still type-checks
  and only the runtime refuses it.
- The fallback factory (139 ns) is within the budget by a small margin.
- A class frozen before its first `meta()` call cannot be given its metadata
  (`Object.defineProperty` throws a `TypeError`).
- `toJSON` is not in the row types (`RowOf` lists fields only), so `user.toJSON()` does not
  compile; `JSON.stringify(user)` does. Adding it would change the contract.

## Requests

**Every later step**

- Get a schema's metadata with `meta(S)`. `S[META]` is the base class's metadata until
  `meta(S)` has run once: right fields, but the wrong name, no associations of `S`, and a
  factory that makes rows without `S`'s getters. Reading `S[META].fields` (as
  `internal/inspect.ts` does) is safe either way.
- The reference schemas are in `@egon-orm/test-support` (`User`, `Post`, …).

**Step 05 (changeset)**

- A nullable field without `.default()` has `FieldMeta.default === undefined`; its value
  in a new record is `null` (decision 4).
- `t.embedMany` fields have a function default returning `[]`.

**Steps 07, 08 (query)**

- `fieldTypeOf(builder)` (internal, `schema/index.ts`) gives the type behind `t.integer()`
  for `param` and `expr.cast`.

**Step 12 (repo reads)**

- Build rows with `meta(S).create(values, meta(S).rowMeta("loaded", schema))`, values in
  `persisted` order. The factory does not convert values (no `fromDb`).

**Step 13 (repo writes)**

- `autogenerate.on` is `"insert"` or `"insertAndUpdate"` (timestamps' `updatedAt`). The
  two timestamps of one insert should share one instant; each calls its own function.
- An integer key with `.primaryKey()` has `dbGenerated: true`; read it back.

**Step 14 (preload)**

- `createWith(names)` checks the names against `assocs()` and caches by the list; keep the
  returned factory on the plan.
- `ResolvedAssoc.unique` is the `manyToMany` option the contract lacks.

**Step 15 (nested changesets and embeds)**

- Embed fields carry `jsonType()` as their `FieldMeta.type` for now; the embed's
  conversion is yours. `EmbedMeta.column` and the embedded schema's `FieldMeta.column` (snake_case
  by default) are the stored names.

**Contract (whoever next opens an ADR on `contracts/schema.ts`)**

- `AssocMeta` has no `unique`; `toJSON` is not in the row type; `primaryKeyOf` cannot be
  typed from a row alone.

**Benchmarks (step 19)**

- `internal/index.ts` still re-exports the built-in types for `types.bench.ts`; now that
  `t` is public, that benchmark could use `t.integer()` and the re-export could go. Both
  files are outside this step's paths, so I left them.
