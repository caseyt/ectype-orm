## Decisions

1. **How a changeset is typed.** `Changeset<S, New>`: `S` is the schema class (or
   `{ data, types }`), `New` is `true` for a new record, `false` for a loaded row, and
   `boolean` when either is possible. `cast`/`change` infer:
   - from a class: `Changeset<typeof User, true>`;
   - from `User | typeof User` (a changeset function's parameter, as in the guide):
     `Changeset<typeof User, boolean>`;
   - from a changeset: its own type; from `{ data, types }`: typed from the builders.
   - **from a row alone** (`change(user, …)` with `user: User`): a row's type does not
     lead back to its class (step 04 status, decision 18), so the changeset is typed with
     `RowSchema<User>`, whose fields are the row type's writable, non-function properties
     (getters without setters are read-only and so left out). Field names and value types
     are exact for the blog schemas.
   To let `change(user)` fit a parameter typed `Changeset<typeof User>`, `cs.model` is
   typed as "a schema class whose rows are `Row<S>`" rather than `S` itself. The cost: the
   statics of the class (its associations) are not visible through `cs.model`, and a
   changeset made from a row alone does not know its association names: `AssocName`
   accepts any string there (the name is checked when the method runs; review round 1).
2. **`applyChanges()` and `applyAction()` on a new record are compile errors** through a
   `this` parameter (and a parameter of `applyAction`) that requires a member no
   changeset has, named after the reason. With `New = boolean` they compile and check at
   run time (`QueryError`).
3. **`changes` holds `null` only for nullable fields.** The spec types every change as
   `| null`, but a non-nullable field can never get a `null` change (item 4), and the
   guide's own example `updateChange("email", (email) => email.trim())` needs `email` to be
   `string`. The guide's overview comment was updated to match.
4. **`undefined` is never a change.** In `cast` a key whose value is `undefined` counts as
   absent; `change` skips such keys; `putChange`, `forceChange` and `updateChange` (when
   the function returns `undefined`) throw `QueryError` pointing at `null` and
   `deleteChange`. The guide said `fetchChange` "tells a change to `undefined` apart from
   no change"; it now says a change to `null`.
5. **Errors for misuse are `QueryError`** (unknown field, association or embed given to a
   field method, bad options, a target that is none of the four kinds, `applyChanges` on
   a new record). `CastError` is only for params that are not a plain object, as the spec
   says.
6. **`null` on a non-nullable field via `putChange`/`forceChange`/`change`** adds
   `can't be blank` once (not repeated) and keeps an earlier change of that field, as a
   failed cast does.
7. **Empty values**: the spec's `[""]` → `null` (not the field's default), compared with
   `SameValueZero`; whitespace-only strings are not empty unless listed; elements inside
   arrays are not filtered.
8. **Casting a changeset again** compares with its changes first, then the data (a value
   back to the record's own value removes the earlier change; review round 1); merges
   params (`{ ...old, ...new }`), changes and errors, leaving out an error equal to one
   already on that key.
9. **`merge`** requires the same schema (or `types`) and the identical data object (or
   both new records), refuses two different non-null actions, and joins `prepare`
   functions too (an `optimisticLock` on the second changeset would otherwise lose its
   increment while keeping its filter).
10. **`validations`** are a backwards-linked list materialised (frozen, cached) on first
    read, so a passing validation allocates one node. Each entry is
    `[field, { validation, …argument, …options }]`, e.g. `["email", { validation: "format",
    pattern }]`; `validateRequired(["a", "b"])` records one entry per field;
    `validateChange` records `{ validation: "change" }`. `addValidation` (step 06) stores a
    descriptor as given.
11. **`validateRequired`** skips a field that already has an error and removes the change
    of each field it finds missing; a new record's defaults count as values.
12. **`validateLength`** counts grapheme clusters with `Intl.Segmenter`, with a fast path
    for ASCII text without a carriage return (property-tested against the segmenter);
    `count: "bytes"` reports `type: "binary"` and `byte(s)`. It throws without a limit or
    with a limit that is not a whole number ≥ 0.
13. **`validateNumber`** throws without a limit, as `validateLength` does (review round 1),
    checks options in the order written (first failure reported),
    accepts `number` and `bigint` limits and fields, treats `NaN` as failing every
    comparison, and validates every option up front (an unknown option throws even after
    an earlier failure).
14. **`validateInclusion`/`validateExclusion` compare with the field type's `equal`**
    (dates by time); `validateSubset` compares elements structurally.
15. **`validateConfirmation`** runs only when the field has a change (not a change to
    `null`), like the other validations (review round 1). It **casts the confirmation
    param with the field's type and compares the result with the change using the type's
    `equal`**; a confirmation that is `null` or rejected by the type is a mismatch (a
    missing one is an error only with `required`; review round 3). This differs from comparing the raw params: the raw
    `password` param may be absent (the change came from `putChange`), and comparing the
    raw confirmation with the cast change fails identical input whenever the type
    changes it (`"36"` becomes `36`, a lowercasing type, a timestamp string). Casting
    both sides the same way makes "the same input typed twice" always match. The `message` option
    applies to both the mismatch and (with `required`) the missing confirmation.
    **`validateAcceptance`** uses the boolean type's cast (`true`, `"true"`, `1`, `"1"`)
    and checks the params whatever changed. Both do nothing on a changeset made by
    `change` (no params).
16. **`validateChange`** results: a string becomes `{ message, meta: {} }` without a
    `validation` key; objects may omit `meta`. Other results throw.
17. **Constraint names**: unique `<table>_<columns>_key`, foreign key
    `<table>_<column>_fkey` (columns, not field names, honouring `.column()`),
    `assocConstraint` the `belongsTo`'s `<table>_<fk column>_fkey` on the association's
    name, `noAssocConstraint` `<child table>_<fk column>_fkey`, and **exclusion
    `<table>_<column>_excl`** (Postgres's own default, per the one-convention decision).
    Schemaless and embedded changesets have no table: a constraint there needs `{ name }`.
18. **`noAssocConstraint`'s message is `is still associated with this entry`** for every
    association kind, as the guide's table says.
19. **`optimisticLock`** computes the next value when declared (default `n + 1`, wrapping
    to 1 after 2147483647; a `bigint` adds `1n`), stores the current value in `filters`
    and a `prepare` function that `forceChange`s the new value. It throws when the field
    has no value.
20. **`validateUniqueAsync`** rejects with `QueryError` until step 13 registers the
    implementation with `provideValidateUniqueAsync`; field names are checked first.
21. **`repo`** is a public member (`unknown`, `null` until the repo sets it with
    `withRepo`), because step 13's `prepare` functions receive a changeset "with `repo`
    set".
22. **`applyChanges()`** builds a new row with the schema's factory, keeping the data's
    `RowMeta`, virtual values and preloaded associations (through `createWith`). Without a
    schema class it returns `{ ...data, ...declared defaults of absent fields, ...changes }`,
    so that it agrees with `getField`.
23. **`params`** is kept as given (not copied); `cast` with `null`/`undefined` stores a
    frozen `{}`; `change` stores `null`.
24. **Without a schema class**, the builders' modifiers apply (`nullable`, `default`,
    `redact`); `.autogenerate()` and `.dbGenerated()` are refused (they mean nothing
    without a table), so `AppliedData` can type a field with a default, or a nullable
    one, as present (review round 1); field names `__proto__` and `constructor` are refused; the derived table is
    cached per `types` object; `model` is `null` and inspect says `Changeset<schemaless>`.
25. **`change(User, values)` takes `Partial` of every field's value, virtual fields
    included** (the spec says `Partial<InsertShape>`, which leaves virtual fields out).
26. **`traverseErrors`** descends into changesets held in `changes`, singly or as an array
    of changesets, adding a key only when a child has errors; a nested tree replaces the
    parent's own errors on the same key. A test pins this; see Requests → Step 15.
27. **Inspect** prints `Changeset<User> { action, changes, errors, valid }`; changes are
    formatted with `formatStruct` and the redacted names; nested changesets are shown as
    their own redacted summary, never with their params or data.
28. **No `any` and no lint suppression.** `cs.prepare` is typed
    `readonly PrepareFunction<S, New>[]`; internal code handles changesets as
    `Changeset<ChangesetSource, boolean>`. (The first push had two
    `biome-ignore noExplicitAny`; both are gone.)

## Known gaps

- The allocation of a passing validation is verified by identity checks and by reading,
  not by a heap-delta test under `--expose-gc`.
- `cs.model` does not expose the class's statics at the type level (decision 1).
- `validateNumber` does not accept `t.decimal()` fields (their values are strings) and
  `validateLength` does not accept `t.binary()` values.
- `emptyValues` takes values only, not predicates.
- On a changeset made from a row alone, a loaded association property (a row typed
  `Loaded<typeof User, "posts">`) types as a field and throws `QueryError` at run time:
  the types cannot tell an association's value (a row or a list of rows) from an embed
  field's or a JSON field's. Pass the class (`User | typeof User`) to avoid it.

## Review, round 3

One blocking finding, a regression from round 2: comparing the confirmation exactly as
sent with the cast change failed identical input whenever the type changes the value
(`{ age: "36", ageConfirmation: "36" }`, a lowercasing type, a timestamp string), and
passed `ageConfirmation: 36`. Fixed: the confirmation is cast with the field's type and
compared with the change by the type's `equal`; a confirmation the type rejects (or
`null`) is a mismatch (decision 15). Tests cover identical strings that the cast changes
(integer, a lowercasing custom type, a timestamp), the mixed case (`"36"` and `36`),
`putChange`, a real mismatch, a rejected confirmation and `null`; the round-2 test that
pinned the opposite results was replaced. The null-change rule is unchanged.
