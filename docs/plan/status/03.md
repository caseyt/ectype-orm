None of the README §7 budgets is measured by this step alone. The two it feeds are
"`cast` + 5 validations on 10 fields < 3 µs" (step 05) and "hydrate a 10-column row
< 150 ns" (step 12). A type whose conversion is `IDENTITY` adds nothing to hydration.

One optimisation was made, with the benchmark that shows it. Reading a `"YYYY-MM-DD"`
string as a `Date` first used a regular expression, three `Number()` calls and `Date.UTC`:
128 µs per 1,000 values. It now reads character codes and computes the day count with
integer arithmetic: 57 µs, of which 28 µs is allocating the `Date`s. The same change took
the date cast from a string from 143 ns to 28 ns. Three property tests (5,000 runs each)
check the arithmetic against the engine's own `Date` for every day of the years 1 to 9999.

## Decisions

Choices the spec left open. Each is covered by tests.

1. **The built-in types are functions named `<kind>Type`** (`integerType()`), exported
   from `types/index.ts` only. A type without options is one shared object.
2. **`IDENTITY` is not public.** `index.test.ts` (step 02) asserts that it is not
   exported. A custom type leaves `fromDb` and `toDb` out and `defineType` fills it in.
3. **`defineType` requires `fromDb` and `toDb` at the type level when `TDb` differs from
   `TApp`**, and lets them be left out when the two are the same. `TDb` defaults to `TApp`.
4. **`defineType` validates the definition** and throws `SchemaDefinitionError`: an empty
   name, a `cast` that is not a function, a malformed `db`, or a `custom` `sql` that does
   not match `CUSTOM_SQL_TYPE` (so the mistake shows where the type is defined, before the
   compiler refuses it).
5. **A type's functions are called without `this`.** `resolveCodec` returns `type.fromDb`
   and `type.toDb` as they are, and `arrayType` holds the element's functions. Wrapping
   them would add a call per value per row. This narrows the `FieldType` contract for
   hand-written type objects that are classes with methods; see "Requests".
6. **Every type has the same six properties in the same order** and is frozen. Nothing
   else is attached to a type. The element type of an array is kept in a `WeakMap`
   (`elementTypeOf`), and a decimal's precision and a timestamp's precision appear only in
   the type's `name`.
7. **integer**: safe integers, as the spec says, not the 32-bit range of the Postgres
   column. `-0` is returned as `0`. Strings longer than 40 characters are rejected before
   parsing.
8. **bigint**: the spec says "integer `number`". I accept only **safe** integers: a larger
   number has already lost digits, and storing a neighbouring value silently is worse than
   `is invalid`. Values outside the 64-bit range are rejected, as the column would.
9. **bigint `{ mode: "number" }`**: its `fromDb` accepts a number, a bigint or a digit
   string and throws `CastError` beyond the safe range. It handles the string itself
   because the range check has to see the driver's value whatever form it arrives in.
10. **float**: numeric strings may have a sign, a fraction and an exponent; at most 400
    characters. `"NaN"` and `"Infinity"` are rejected.
11. **decimal**:
    - Strings may not have an exponent. Numbers that print with one (`1e21`, `1e-7`) are
      written out in full.
    - The result is in a normal form: no `+`, no leading zeros, no bare point, no negative
      zero. Fraction digits are kept as written (`"19.990"` stays `"19.990"`).
    - With `{ precision, scale }` the value is rounded to `scale` half away from zero,
      which is how Postgres rounds `numeric`, and padded to `scale`. A number with more
      than `precision - scale` digits before the point is rejected. `scale` defaults to 0,
      as in SQL. Rejecting extra fraction digits instead would have made `0.1 + 0.2`
      invalid for a two-digit column.
    - `equal` compares numerically (`"1.50"` equals `"1.5"`), because the database returns
      the column's scale and a changeset would otherwise see a change that is not one.
12. **boolean**: exactly the eight inputs of the table. `"TRUE"`, `"yes"` and `2` are rejected.
13. **date**: years 1 to 9999. The `{ year, month, day }` form accepts whole numbers or
    digit strings (form input). With `{ as: "date" }` the driver value is the
    `"YYYY-MM-DD"` string (`FieldType<Date, string>`): `fromDb` parses it to midnight UTC
    and throws `CastError` for `"infinity"` or a BC date; `toDb` writes the UTC date.
14. **time**: normalised to what the database returns: seconds always present, no trailing
    zeros in the fraction.
15. **timestamp and localTimestamp**:
    - The spec's table says both "truncates to seconds unless `{ precision }`" and "default
      ms". I read it as: `precision` is `"s" | "ms" | "us"`, default `"ms"`.
    - `"s"` drops the milliseconds of accepted input (towards the earlier second, also
      before 1970). It does not touch `fromDb`.
    - `"us"` is a distinct type (`timestamp(us)`) that behaves like `"ms"`: a JavaScript
      `Date` cannot hold microseconds. It exists so that a column can be declared with
      microsecond precision. See "Known gaps".
    - Strings are matched against a grammar, never handed to `Date.parse`. The separator
      may be `T`, `t` or a space; seconds are optional; the offset may be `Z`, `±HH`,
      `±HHMM` or `±HH:MM`. Fraction digits beyond three are dropped.
    - A plain `Date` is returned as the same object. An instance of a `Date` subclass is
      copied into a plain `Date`, because its methods may be overridden and `equal` calls
      `getTime`. A number (epoch milliseconds) is rejected: the table lists only `Date`
      and strings.
16. **json**: "any JSON-serialisable value" is read as "any value JSON represents
    exactly". `undefined` inside a document, `NaN`, `Date`, `Map`, class instances,
    `bigint`, functions, cycles and nesting deeper than 500 are rejected, because they
    would be stored as something other than what was passed, or would throw in the driver
    at query time. The shape `T` is not checked. `cast` returns the same object, not a copy.
17. **array**: a `null` or missing element is rejected by `cast`, with its index (the
    element type has no way to say it is nullable, and `T[]` has no `null`). `fromDb`,
    `toDb` and `equal` pass a stored `NULL` element through without calling the element
    type. A failed element's `message` and `meta` are kept, and `index` is added.
18. **enum**: a mapping's values are all strings (`text`) or all whole numbers
    (`integer`), and distinct. When a key and a stored value are spelled the same, `cast`
    takes the input as the key. `fromDb` of a value that is not in the mapping throws
    `CastError`. Every enum is named `enum`.
19. **`resolveCodec`** takes `Pick<Adapter, "typeOverrides">` and caches in a `WeakMap` per
    adapter object. For an array type that the adapter does not override, the element
    type is resolved through the adapter too and applied per element, so overriding
    `bigint` also fixes `bigint[]`. An override of the array type itself wins.
20. **`parameterized`** keys its cache on the options' content: plain objects whatever
    their key order, arrays in order, primitives by value and type. A type, a function, a
    symbol or a class instance is compared by identity.
21. **`deepEqual`** treats `0` and `-0` as equal (JSON cannot tell them apart), `NaN` as
    equal to `NaN`, and two objects with different prototypes as different.
22. **No error message contains the offending value**, since the field may be redacted.

## Known gaps

- `t` does not exist yet (first Acceptance box).
- `timestamp({ precision: "us" })` cannot carry microseconds. Reading a
  `timestamptz(6)` value into a `Date` drops them, so a row written back loses them. A
  type that keeps them would need another application type than `Date`.
- `integer` accepts values beyond the 32-bit range of a Postgres `integer` column. Such a
  value fails in the database, not in the changeset.
- Casting a timestamp from an ISO string costs about 300 ns, most of it the regular
  expression. I did not hand-write that parser: the grammar has several optional parts, and
  no budget is at risk from it yet.
- Nothing here ran against a database. That each driver produces and accepts the
  representations listed under "Requests" is for steps 11 and 17 to verify.

## Requests

**Step 04 (schema)**

- Wrap the functions in the table above. `t.array(inner)` passes the inner builder's type
  to `arrayType`; `t.type(custom)` takes the type as it is.
- A builder has to expose its `FieldType` to `param`, `expr.cast` and schemaless changesets.
- Convert the two remaining hand-written blocks of `guide/types.md`.
- Once `t` is public, the benchmarks can use it and the `types` re-export in
  `internal/index.ts` can be removed.

**Step 05 (changeset)**

- A failed cast may carry `message` and `meta`; an array's failure has `meta.index`.
- Cast results can be shared frozen objects (`INVALID`, both boolean results, every enum
  result). Do not mutate a `CastResult`.
- `equal` for `decimal` is numeric, and for `json` structural.

**Steps 10 and 12 (compiler, repo reads)**

- Get conversions from `resolveCodec(type, adapter)`, once per column per plan. The
  returned object is frozen and its functions are plain functions: call them without a
  receiver, and skip the call when the function is `IDENTITY`.
- `fromDb` may throw `CastError` (`bigint(number)`, `date(date)`, a mapped enum).

**Steps 11 and 17 (adapters)**

- The representations the types expect from a driver, and hand to it:

  | `db.kind` | Driver value |
  |---|---|
  | `integer`, `float` | `number` |
  | `bigint` | `bigint` for the `bigint` type. `bigint(number)` reads a number, a bigint or a digit string by itself. |
  | `decimal` | `string` |
  | `boolean` | `boolean` |
  | `text`, `uuid`, `time` | `string` |
  | `binary` | `Uint8Array` (a `Buffer` is one) |
  | `date` | the `"YYYY-MM-DD"` string, for both `date` types |
  | `timestamptz` | `Date` |
  | `timestamp` | a `Date` whose **UTC** fields are the wall time |
  | `json`, `jsonb` | the parsed value |
  | `array` | a JavaScript array, `null` for a `NULL` element |

- For `pg` that means: `int8` needs an override for the `bigint` type (text to `BigInt`);
  `date` must arrive as the raw string (the default parser builds a local-midnight
  `Date`); `timestamp` without a time zone must be read as UTC (the default parser reads
  it in the process's zone); a `json` parameter must be serialised by the adapter (`pg`
  writes a JavaScript array as a Postgres array literal and a bare string as text).
- An override replaces the type's own conversions, it does not wrap them. So dispatch on
  the type and not only on `db.kind`: `bigint` and `bigint(number)` share a kind, as do
  `date` and `date(date)`, and an override meant for the first would break the second.
- Override element types, not array types, unless the dialect has no arrays:
  `resolveCodec` applies an element's override to each element.

**Step 18 (migrations)**

- A decimal's precision and scale and a timestamp's precision are only in the type's
  `name`. If migrations need them as data, the place for them is a lookup beside
  `elementTypeOf`, not a property on the type (decision 6).

**Contracts (`contracts/type.ts`)**

- The `FieldType` documentation could say that `fromDb`, `toDb`, `cast` and `equal` are
  called without a receiver (decision 5). It is a clarification, not a change of shape.
